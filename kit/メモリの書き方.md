# メモリの書き方

Claude Code のメモリは、**プロジェクトごとの専用ディレクトリ**に置かれるファイル群です。置き場は `/memory` で確認できます。

考え方は1つだけ。**1ファイル＝1つの事実。**

## ファイルの形

```markdown
---
name: <短いkebab-case-のスラッグ>
description: <1行の要約。関連するかどうかの判定に使われる>
metadata:
  type: user | feedback | project | reference
---

<事実の本文。feedback と project は「なぜそうなのか」と「どう適用するか」を続けて書く。
関連するメモリは [[相手のname]] で結ぶ。>
```

## 4つの型

| type | 何を入れるか |
|---|---|
| `user` | あなたが誰か（役割・技術レベル・好み・使っている環境） |
| `feedback` | 仕事の進め方についての指示。**訂正も、うまくいった型も両方。理由を必ず書く** |
| `project` | 進行中の作業・目標・制約で、**コードやgit logからは読み取れないもの** |
| `reference` | 外部リソースの所在（URL・ダッシュボード・チケット） |

## 索引（MEMORY.md）

`MEMORY.md` は毎セッション自動で読み込まれる索引です。**1メモリ1行**。

```markdown
- [タイトル](ファイル名.md) — 一言の手がかり
```

**索引に内容そのものを書かない。**索引が太ると毎セッションのコストになり、しかも詳細ファイルと食い違って事故ります。

## 書くもの・書かないもの

**書く**
- 明示した基準・NGライン・**その理由**
- 何かを選んだ判断と、その根拠（半年後の自分が理由を思い出せない）
- 相対的な日付は**絶対日付に直して**書く（「来週」は1週間で無意味になる）

**書かない**
- コードを読めば分かること（構成・関数名・過去の修正内容）
- git log に残っていること
- `CLAUDE.md` に既に書いてあること
- その会話の中だけで意味を持つこと

## 更新のしかた

- 保存する前に、**既に同じことを書いたファイルがないか確認する**。あればそれを更新する（重複させない）
- **間違いだと分かったメモリは削除する。**古い判断が残っていると、それが次の判断を汚します
- 新しい情報と既存のメモリが矛盾したら、**現状を優先**してメモリを直す
- 更新は毎ターンではなく**節目でまとめる**（重要な判断・段階完了・仕様変更・デプロイ）。書き換え自体にコストがあります

## ひとつ注意

メモリは**書かれた時点で正しかったこと**を記録しています。ファイル名・関数名・フラグを名指ししているメモリは、**それが今も存在するか確認してから**使ってください。
